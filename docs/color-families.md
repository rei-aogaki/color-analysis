# 色の傾向：系統別集計と場所の確認

追加日：2026-10-19。実装：0.2.0。方式ID：`oklch-family-v1`。ユーザーが「色系統別の割合＋分類場所の確認」を主にする方向性に合意したことに基づく。

## 1. 変更の理由

写真では、似て見える青でも照明・陰影・質感によって多数のRGB値に分かれる。完全一致の上位10色は画像全体のごく一部しか説明しない場合があり、「その他」が大半を占めても、青系が少ないとはいえない。

そこで「青系の面積が何％か」を直接調べる色系統別集計を初期モードにする。完全一致・固定幅の類似色集計も選択可能なまま残す。代表色の自動抽出は今回追加していない。色系統への分類は近似的なルールだが、分類後の件数は全対象画素を漏れなく数える。

画像・名前・結果を外部へ送信せず、永続保存しない方針は変更しない。実ユーザーの写真・スクリーンショットをリポジトリの検証資産へ追加しない。

## 2. 画面と操作

初期モードは「色の傾向」。画像選択後に「解析する」を押す。青・赤などの系統と白・グレー・黒に近い色を、件数と割合で表示する。全対象画素を分母にする。半透明はalphaによる重み付けをせず1画素とし、背景と合成しない。完全透明は既定で除外し、含める設定なら独立した系統にする。

系統のボタンは件数が多い順に表示する。A案への統合後は0件の系統を「使われていない系統」に折りたたみ、開いて確認できるようにする（0件は選択不可）。グラフと表は存在する全系統を表示し、上位10件で打ち切らず、「その他」も作らない。統計の「使われている系統」は0件を除く数。色系統モードではHEX検索を無効にし、全系統を確認できるようにする。完全一致・固定幅分類の検索・ページ操作は維持する。

ボタンの色見本は系統を識別するための固定色であり、入力画像の実際の平均色とは限らない。帯グラフ・表の色見本には所属画素の平均RGBを使い、表の「系統 / 平均色」で区別する。

系統ボタンを押すと、元画像プレビューの該当箇所だけを元の色で残し、それ以外を暗くする。ボタンはタッチ・マウス・キーボードで操作でき、選択状態をaria-pressedで示す。「元画像に戻す」で解除できる。完全透明の位置は見えないため、選択時のみ青い印で表示し、その説明を併記する。

強調表示中も、画素検査は原本バッファのRGBAを返す。表・グラフ・分母・ダウンロード内容を選択した系統だけに絞らない。クリア・画像変更・条件変更・再解析は強調表示とラベルを破棄する。素早い切替では古い表示処理を無効化し、最後の操作だけ反映する。

## 3. 標準分類ルール

ブラウザ取得後の8bit sRGBを線形化し、D65基準のOklabへ変換。L（明るさ）、C（色みの強さ）、h（色相角）で分類する。背景となる色表現は[W3C CSS Color 4](https://www.w3.org/TR/css-color-4/#ok-lab)を参照。色名・境界値はこのアプリの設計値であり、W3Cが定めた色名分類ではない。

まずalpha=0を完全透明へ分類する。それ以外でC<0.015なら無彩色に近いとみなし、L<0.25なら黒に近い色、L≥0.90なら白に近い色、その間をグレー系にする。C≥0.015はhで分類する。hは0以上360未満に正規化する。

| キー | 系統 | hの範囲（度） |
|---|---|---|
| 0 | 赤系 | [0,40) または [355,360) |
| 1 | 橙・茶系 | [40,75) |
| 2 | 黄系 | [75,110) |
| 3 | 黄緑系 | [110,135) |
| 4 | 緑系 | [135,175) |
| 5 | 青緑系 | [175,210) |
| 6 | 青系 | [210,285) |
| 7 | 紫系 | [285,325) |
| 8 | 桃・赤紫系 | [325,355) |
| 9 | 白に近い色 | C<0.015かつL≥0.90 |
| 10 | グレー系 | C<0.015かつ0.25≤L<0.90 |
| 11 | 黒に近い色 | C<0.015かつL<0.25 |
| 12 | 完全透明 | A=0（全画素を含める設定の場合のみ対象） |

### 境界値の理由と制約

- RGBの大小だけで青を決めず、色相を使うことで明るい青・暗い青・くすんだ青を合わせて集計する。
- ほぼ無彩色ではわずかなRGB差から不安定な色相が付くため、Cの小さい部分を先に分ける。閾値を高くしすぎると青みグレーまでグレーになるので、初期の固定値として0.015を用いる。
- 明るさだけで白・黒へ分けない。色みが十分残る暗い青は青系に残す。
- 茶は橙系の暗い色と関連するため「橙・茶系」と表記し、桃と赤紫も一つにまとめる。分類数を増やしすぎず全体を比較できる粒度にする。
- 色相角の間隔はRGBの色名区間と同一ではない。Oklabの原色、無彩色、複数の青の既知値と境界でテストし、採用値を明記する。
- これらは色名の唯一の正解ではなく、系統ごとの面積比率も写真の印象・注目度・物体の種類を示す指標ではない。髪・肌などの物体認識は行わない。特定の写真を期待どおりの割合にするために閾値を調整しない。

閾値を変えると件数が変わるため、新しいルール版を付け、理由と比較結果を記録する。UIには最初から細かい調整項目を増やさず、複数の合成データ・利用者の確認結果を踏まえて見直す。

## 4. 内部・データ契約

`src/analysis/families.ts`が色変換・分類定義を持ち、Workerで全画素を分類する。sRGB線形化は256要素の参照表を使い、画素のサンプリングや画像縮小をしない。13系統分の件数とRGB合計を保持する。画面・出力の平均RGBは所属画素の成分ごとの算術平均を四捨五入した値であり、最頻のカラーコードや知覚的な代表色とは区別する。

各画素にUint8の系統ラベルを一つ付け、除外画素は255とする。Workerからラベルバッファの所有権をメイン側へ転送し、再複製を避ける。概要・表は従来どおりWorker側の集計を利用する。`sum(count)=対象画素数`、ラベルの各キーの件数と各行のcountが一致することを検証する。

強調表示はメイン側で原寸ラベルを参照し、別の表示用ImageDataを分割処理で生成する。元のImageDataは書き換えない。処理中の選択切替・クリアを世代番号で検知し、旧処理を破棄する。強調表示の準備に失敗したら原画像へ戻し、集計結果を残す。

追加メモリはラベルが画素数×1バイト、選択中の表示用RGBAが画素数×4バイト。1600万画素ではそれぞれ約16MB・64MBが必要で、これ以外にも原画素・Canvas等がある。モバイルのピークメモリ・最大画像での表示応答は引き続き実測対象。

### 出力の変更

アプリ版は0.2.0、JSON/CSVのschemaVersionは2へ変更。JSONは色系統モードにclassification（方式版、C/L閾値、h境界）を付け、各rowにfamily（系統名）を付ける。keyは上表の安定キー、rgbは所属画素の平均色、alphaは通常null、完全透明だけ0。その他のモードはclassification/familyを追加しない。

CSVは既存列の末尾にfamily・classificationRuleを追加する。系統名はアプリ固定の文字列のみで、元画像名などの自由文字列は含めない。CSVのclassificationRuleは`oklch-family-v1`で、本書と対応する。比率は0〜1の有限精度値、表示だけパーセントに丸める。空結果のCSVは従来どおりヘッダーだけ。強調表示の選択情報やラベル画像を出力しない。

## 5. 今回の確認

単体テスト15件が成功。原色・無彩色、明暗とくすみのある青、C/L/hの境界、全ラベルと件数、透明部分、CSV/JSONの方式名を検証した。

Chromiumのブラウザ検証では、新モードが初期値であること、13系統の全件表示、青の多数のコードを含む合成画像が青系80%になること、強調箇所の画素、解除、透明位置の青印、素早い切替・クリア、強調表示前後で保存内容が変わらないこと、タッチ操作を確認。既存モード・形式・保存・通信・永続保存・サブパスの回帰検証も実施した。実ユーザーの添付画像を統計算出やテスト資産化には使用していない。

直近のChromium 148.0.7778.96でのブラウザ検証は13グループが成功。400万画素の合成RGBA配列を色系統へ分類しラベルを転送する試験は約0.52秒、ラベル配列は400万バイトだった。単回・単純な合成データでの結果で、画像復号・強調表示の生成・端末全体のピークメモリは含まない。完全一致の速度やスマホ実機の速度と同一視しない。

スマホ実機・他ブラウザ、多様な写真に対する分類の納得感、最大規模の強調表示のピークメモリは未確認であり、今回の成功を全画像での分類の正しさや人の印象との一致として扱わない。
